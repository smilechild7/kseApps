01 · CONTEXT & CONTRIBUTIONS

전환 배경과 담당 범위

전환의 배경

정밀한 사진 편집과 멀티스레드를 활용한 데이터 미리보기 개선 요구가 있었습니다. 기존 React Native 구현에서 이 요구를 풀기 위한 제약을 계기로, 대표가 네이티브 전체 재구현을 결정했습니다.

Android 개발 전담

대표가 iOS를 담당하고, Android 개발은 전담했습니다. Kotlin·Jetpack Compose로 주요 탭과 상세 화면, 지도, 글쓰기·사진 처리와 API 연동을 구현하고 UI 디자인 회의에도 참여했습니다.

02 · HOMESCREEN SCROLL PERFORMANCE

홈 스크롤의 병목을 나누어 개선

여러 가로 목록을 세로로 쌓은 HomeScreen에서 빠르게 스크롤할 때의 끊김을 다뤘습니다. 재구성 범위, 이미지 초기화, 카드 측정과 헤더 처리의 반복 작업을 줄이고, 릴리스 빌드를 직접 사용하며 스크롤을 확인했습니다.

화면 구조 LazyColumn → 섹션별 LazyRow·HorizontalPager → 사진 카드

해결 과제

빠르게 스크롤하면 사진 카드 여러 개가 한꺼번에 화면에 들어왔습니다. 이때 새 카드의 구성·이미지 초기화·측정 비용이 누적됐고, 스크롤을 따라 움직이는 헤더의 상태 갱신도 함께 처리해야 했습니다.

설계 판단

Android Studio에서 캡처한 디버그 빌드의 trace로 비용이 누적되는 구간을 분석했습니다. 상태를 읽는 범위부터 카드 구성과 측정까지 단계적으로 변경하고, 릴리스 빌드의 육안 확인 후 불필요한 TextStyle 캐시는 제거했습니다.

확인 방법과 범위

디버그 trace는 병목 진단에 사용했고, 릴리스에서는 직접 스크롤하며 끊김을 육안으로 확인했습니다. 당시 trace와 상세 측정 환경이 남아 있지 않아, 정량적인 릴리스 성능은 이 기록으로 판단할 수 없습니다.

개선 과정 · 재구성에서 헤더 처리까지
  1. 01 · 2026.06.01

    스크롤에 따라 다시 구성되는 범위 줄이기

    헤더 위치 등 자주 바뀌는 값을 offset·graphicsLayer·레이아웃 단계에서 읽도록 조정했습니다. 모델의 안정성을 정리하고 Store와 섹션 인자를 ImmutableList로 전환했으며, 가로 목록에 항목 키와 contentType을 지정했습니다.

  2. 02 · 2026.06.02

    새 카드마다 반복되는 이미지 초기화 줄이기

    빠른 스크롤 중 AsyncImagePainter의 초기화 비용이 카드마다 누적되는 지점을 확인했습니다. HomeScreen의 이미지 표시 9곳을 FastAsyncImage로 교체해 LaunchedEffect에서 ImageLoader.execute()를 호출하고, Coil 로더와 캐시는 그대로 공유했습니다.

    변경한 홈 카드의 이미지 경로LaunchedEffect(uri) → ImageLoader.execute() → Image(bitmap)
  3. 03 · 2026.06.02

    카드의 측정·배치와 로딩 준비 비용 줄이기

    이미지를 감싸던 중복 Box를 제거하고 해당 modifier를 이미지에 적용했습니다. Spacer 일부는 padding·spacedBy로 바꿔 간격을 유지하면서 노드 수를 줄였습니다. 로딩용 임시 항목 수도 줄여 목록 생성과 묶음 계산의 부담을 낮췄습니다.

  4. 04 · 2026.06.05

    헤더 스크롤의 멈춤과 터치 지연 처리

    onPreScroll마다 실행하던 코루틴과 snapTo를 동기 상태 갱신으로 교체했습니다. 스크롤 연결 객체는 유지하고 최신 헤더 높이를 참조하게 했으며, 측정 도중 상태를 쓰던 코드는 onSizeChanged로 옮겼습니다.

    표시용 목록은 remember(places)로 재사용하고, 페이지마다 반복하던 Map 상태 구독은 페이저 바깥으로 모았습니다. 콘텐츠의 관성 스크롤이 헤더 애니메이션의 종료를 기다리지 않도록 분리했습니다.

  5. 05 · 2026.06.22

    같은 구조의 홈 섹션 재사용 보강

    세로 목록에서 반복되는 HomeDefaultSection에도 contentType을 지정했습니다. 안쪽 카드뿐 아니라 바깥 목록의 섹션 구조도 재사용 기준에 포함했습니다.

  6. 06 · 2026.07.02

    릴리스에서 불필요한 최적화 다시 걷어내기

    초기에 추가했던 최상위 TextStyle 캐시 9개는 릴리스 빌드에서 직접 스크롤을 확인한 뒤 제거했습니다. 별도 캐시를 유지할 필요성을 다시 검토해 코드 복잡도를 줄였습니다.

설계 비용 경량 이미지 경로는 crossfade·범용 error painter 등을 생략하고 비트맵 Drawable을 전제로 했습니다. 적용 화면에서 필요한 기능을 확인하고, 다른 용도의 범용 이미지 컴포넌트는 유지했습니다.

03 · NAVIGATION & STATE

탭을 이동해도 탐색은 이어지도록

탭별 백스택과 지도 인스턴스를 분리해 유지했습니다. 상세 화면에서 돌아왔을 때 이전 장소와 탐색 위치를 다시 보여주도록 연결했습니다.

해결 과제

탭 이동이나 상세 화면 진입 때문에 지도와 목록이 초기화되면, 사용자는 방금 보던 장소를 다시 찾아야 했습니다.

설계 판단

화면의 이동 이력과 지도 View의 수명을 분리했습니다. 공통 상세 라우트는 재사용하면서 각 탭이 자신의 백스택을 갖게 하고, 지도는 NavHost 바깥에서 유지했습니다.

상세 구현 · 상태와 작업의 수명

상태 변경은 Store·ViewModel의 함수로 모으고, UI에는 읽기 전용 StateFlow를 노출했습니다. 글쓰기는 루트에서 모달로 진입하는 별도 흐름으로 구성했습니다.

목록·그리드·페이저의 위치는 섹션별 키로 저장했습니다. 스크롤이 멈춘 시점에 위치를 기록하고, 복원할 때는 달라진 항목 수에 맞춰 인덱스를 보정했습니다. 무한 반복 페이저는 내부 인덱스 대신 실제 콘텐츠의 페이지를 기준으로 복원했습니다.

설계 비용 지도와 백스택을 따로 유지하는 만큼 뒤로가기·시트 복원·가시성 관리가 복잡해졌습니다. 전역 Store는 테스트에서 교체하기 어렵다는 점도 남았습니다.

04 · PHOTO EDITING & LIFECYCLE

사진 편집부터 복원·감상·업로드까지

사진의 자르기·회전·반전부터 재편집과 임시저장 복원, 전체화면 뷰어, 업로드와 파일 정리까지 구현했습니다. 화면을 옮기거나 글쓰기를 다시 열어도 원본과 편집 상태를 이어가도록 관리했습니다.

01편집원본 좌표와 결과 이미지02상태 복원원본·편집 정보 보존03뷰어제스처와 화면 전환04업로드·파일 관리변경분 전송과 참조 정리
  1. 01

    편집 · 화면에서 본 영역을 결과 이미지로

    회전된 사진에서는 화면의 자르기 영역과 원본 픽셀 좌표가 어긋날 수 있었습니다. 사진의 회전 메타데이터를 먼저 반영하고, 화면 좌표를 원본 픽셀 좌표로 변환한 뒤 자르기·회전·반전을 적용했습니다.

    상세 구현 · 좌표 변환과 편집 결과

    자유 비율과 1:1·3:4·4:3·9:16·16:9 등의 고정 비율을 지원했습니다. 자르기 영역은 이미지 경계 안으로 제한하고, 90도 회전 시에는 가로·세로 비율과 반전 축을 함께 보정했습니다.

    결과 이미지 생성 순서원본 회전 반영 → 화면의 자르기 좌표를 픽셀로 변환 → 자르기 → 사용자 반전·회전 적용

    비트맵 생성과 파일 저장은 IO 작업으로 분리하고, 편집 결과는 별도 파일로 저장했습니다. 다시 편집할 때 사용할 원본도 함께 추적했습니다.

  2. 02

    상태 복원 · 앨범을 옮기고 다시 열어도 이어서

    앨범 이동이나 사진 목록 갱신으로 편집본이 원본으로 돌아가는 문제를 다뤘습니다. 사진 ID를 기준으로 목록·선택 상태에 편집 결과를 함께 반영하고, 임시저장에는 원본·편집본 URI와 편집 정보를 기록했습니다.

    상세 구현 · 원본 보존과 재편집

    편집 결과의 치수·회전 정보와 자르기 영역·반전·선택 비율을 직렬화했습니다. 다시 열 때는 원본 이미지 위에 편집 상태를 복원해, 이미 잘린 결과물을 다시 자르는 방식으로 품질과 편집 범위가 줄어들지 않도록 했습니다.

    이전 자르기 영역을 이미지 영역에 대한 상대 좌표로 바꾸고, 새 화면의 이미지 영역에 다시 매핑했습니다. 기기 목록을 인덱싱된 목록으로 교체할 때도 선택한 편집본 URI를 유지했습니다.

  3. 03

    뷰어 · 확대·넘김·닫기를 상태에 따라 구분

    기본 배율에서는 좌우 넘김과 수직 드래그 닫기를, 확대 상태에서는 사진 내부 이동을 처리했습니다. 손가락 중심을 기준으로 확대하고, 손을 뗐을 때의 관성과 경계 복귀를 X·Y축별로 관리했습니다.

    상세 구현 · 제스처와 화면 전환

    확대와 경계 저항

    핀치와 더블탭으로 확대하고, 손을 떼면 1–3배 범위로 복귀하도록 했습니다. 입력값과 표시값을 분리해 경계 저항이 반복 적용되는 떨림을 막았습니다.

    축별 관성

    축마다 Animatable을 두어 한 축이 경계에 닿아도 다른 축은 감속을 이어가게 했습니다. 새 터치가 시작되면 진행 중인 관성을 멈췄습니다.

    열기와 닫기

    썸네일의 위치·크기에서 전체화면으로 펼쳤습니다. 닫기 버튼·뒤로가기는 원본 위치로 복귀하고, 수직 드래그 닫기는 화면 밖으로 이동하게 했습니다.

    Predictive Back 진행도에 따라 전환을 적용하고, 취소하면 스프링으로 복원했습니다. 원본 셀의 위치를 알 수 없는 사진은 페이드로 닫았습니다.

    설계 비용 확대·이동·닫기의 입력 우선순위와 전환 상태를 함께 관리해야 했습니다. Dialog 해제 안정성을 위해 하드웨어 비트맵을 피한 선택은 메모리 비용을 늘릴 수 있습니다.

  4. 04

    업로드·파일 관리 · 변경한 사진과 파일 수명 구분

    업로드 전 사진을 긴 변 기준 최대 2048px로 변환했습니다. 리뷰 수정에서는 기존 서버 사진과 새로 추가한 사진을 구분해 신규 사진만 업로드하고, 삭제한 사진은 ID 목록으로 전달했습니다.

    상세 구현 · 이미지 변환, 파일 정리, 갤러리 저장

    먼저 이미지 치수를 읽고 샘플링해 디코딩한 뒤, EXIF 회전과 리사이즈를 적용해 업로드용 JPEG를 생성했습니다. 변환용 임시 파일과 글쓰기의 편집본 파일은 별도로 관리했습니다.

    업로드 후 편집본을 정리할 때는 다른 임시저장 글에서 참조하는지 확인했습니다. 리뷰 수정이 끝나면 게시글을 다시 조회해 홈·타임라인·프로필에 결과를 반영했습니다.

    갤러리 저장은 Coil 디스크 캐시의 바이트를 우선 사용하고, 캐시를 사용할 수 없으면 비트맵을 JPEG로 변환했습니다. 저장 작업은 뷰어를 닫아도 이어지도록 앱 수명의 코루틴에서 실행했습니다.

05 · ANDROID UI & DEVICE ADAPTATION

화면 크기와 시스템 동작을 고려한 Android UI

UI 디자인 회의에서 뒤로가기·시스템 내비게이션 바와 폴더블의 넓은 화면을 고려한 조정을 요청했습니다. 구현에서는 화면 폭에 따른 배치, 콘텐츠 크기 제한, 시스템 영역과 키보드 여백을 다루고 에뮬레이터에서 직접 확인했습니다.

01

넓어져도 과도하게 커지지 않게

화면 폭을 구간별로 나누고 구성 변경 시 크기 정보를 갱신했습니다. 넓은 화면의 홈 페이저는 카드 폭을 제한하고, 사진·배너의 확대 비율에도 상한을 두었습니다.

시스템 내비게이션 바 높이를 하단 탭 영역에 반영하고, 편집·입력 화면에는 내비게이션 바와 키보드 인셋을 적용했습니다. 뒤로가기는 지도 검색 종료와 페이지 복귀의 우선순위를 구분했습니다.

06 · RECENT-PHOTO VISIT NUDGE

최근 사진에서 시작되는 방문 넛지

사진 접근과 위치 메타데이터 권한을 확인한 뒤, 최근 사진을 단서로 “이 장소에 다녀오셨나요?”라고 묻는 넛지를 구현했습니다. 음식 분류는 기기에서 수행하고, 주변 장소 검색에는 방문 묶음의 대표 좌표를 전달했습니다.

해결 과제

방문 사진을 찍은 뒤에도 리뷰를 쓰려면 사용자가 직접 글쓰기를 시작하고 장소를 찾아야 했습니다. 최근 사진을 단서로 앱이 먼저 방문을 묻고, 기록을 시작할 계기를 제공하고자 했습니다.

설계 판단

로그인 상태에서 권한 조건을 충족하면 최근 사진을 확인하고, 비슷한 시간과 위치에서 찍힌 사진을 하나의 방문으로 묶었습니다. ML Kit의 음식 라벨에 주변 장소의 메뉴·업종·거리·촬영 당시 영업 여부를 조합해 후보를 정했습니다.

추정한 장소를 사진과 함께 팝업으로 제안하고, 사용자가 다른 후보를 고르거나 닫을 수 있도록 했습니다.

상세 구현 · 방문 묶음, 음식 분류, 후보 정렬
  1. 방문 단위로 묶기최근 24시간의 사진 중 위치가 있는 사진을 추리고, 30분·100m 기준으로 방문을 나눕니다.
  2. 음식 라벨 추출방문마다 최대 5장의 사진을 기기에서 분류하고, 음식 관련 라벨과 신뢰도를 모읍니다.
  3. 주변 장소 비교묶음의 평균 좌표 주변을 조회하고, 라벨과 메뉴·업종의 일치 정도에 거리·영업시간을 반영합니다.

READ_MEDIA_IMAGES 등 해당 Android 버전의 사진 접근 권한과 ACCESS_MEDIA_LOCATION을 확인했습니다. Android 14 이상에서 선택한 사진에만 접근할 수 있는 경우에는 이 자동 분석을 건너뛰었습니다. 최근 24시간의 사진을 프로세스당 한 번 백그라운드에서 확인하고, 사진 수와 장소 조회 횟수를 제한하며 연속 조회 실패 시 중단했습니다.

사진 분류는 기기에서 수행하고, 주변 장소를 찾을 때는 방문 묶음의 대표 좌표를 서버 검색에 전달했습니다. 영업시간 정보가 없으면 중립적으로 처리하고, 촬영 시각에 닫힌 장소에는 감점을 적용했습니다.

설계 비용 GPS 오차와 음식 분류의 모호함 때문에 한 장소를 단정하기 어렵습니다. 여러 후보와 선택 UI를 함께 제공하고, 사진 위치 정보가 없는 경우는 분석 대상에서 제외했습니다.

07 · PHOTO & PLACE COMPOSING

사진과 장소를 연결하는 글쓰기

글쓰기에서 사진을 고르면 촬영 위치 주변의 장소를 추천하고, 장소를 고르면 ‘장소 주변 사진’ 앨범을 보여주도록 구현했습니다. 사용자가 어느 쪽부터 선택하든 작성 흐름을 이어갈 수 있게 했습니다.

해결 과제

사진을 첨부한 뒤 장소를 다시 검색하거나, 장소를 고른 뒤 갤러리에서 촬영 날짜를 떠올리며 사진을 찾아야 했습니다. 먼저 선택한 정보로 다음 선택을 도울 필요가 있었습니다.

설계 판단

사진에서 시작할 때는 선택한 사진의 GPS로 주변 장소를 조회해 추천 칩을 보여줬습니다. 장소에서 시작할 때는 미리 인덱싱한 EXIF 위치를 Room에서 조회해 관련 사진 앨범을 구성했습니다.

추천 장소를 바로 선택하거나 별도 장소 검색으로 이어갈 수 있게 하고, 기준 좌표가 달라질 때 추천을 갱신했습니다.

상세 구현 · 백그라운드 인덱싱과 좌표 검색
  1. MediaStore기기 사진 목록과 ID를 확인합니다.
  2. EXIF → Room위치 메타데이터를 로컬 데이터베이스에 저장합니다.
  3. 좌표 범위 쿼리선택한 장소 주변의 후보 사진을 조회합니다.

위·경도에 서로 다른 오프셋을 적용한 사각 범위로 후보를 추렸습니다. 사진 메타데이터는 Room에 인덱싱해 기기 안에서 조회하고, WorkManager로 신규·삭제 사진을 반영했습니다.

반대 방향의 글쓰기 흐름에서는 선택한 사진 중 첫 GPS 좌표를 서버 검색에 전달해 주변 장소 후보를 보여줬습니다. 사진을 고른 뒤 장소를 붙이거나, 장소를 고른 뒤 관련 사진을 찾는 흐름을 모두 지원했습니다.

설계 비용 초기 인덱싱에는 시간이 필요하고, 접근 권한이나 GPS가 없는 사진은 후보에서 빠집니다. 신규·삭제 ID 중심 동기화는 기존 사진의 메타데이터 수정까지 추적하지 않습니다.

선택 이후의 편집·임시저장·업로드는 사진 처리의 수명 관리에서 이어서 설명합니다.

08 · MAP INTEGRATION & SYNC

저장한 장소를 로컬과 서버에서 일관되게

저장한 장소를 로컬 데이터로 먼저 보여주고, 서버의 추가·수정·삭제 내역을 동기화했습니다. 장소 지도에서는 화면에 보이는 영역을 우선 조회하도록 요청 순서를 구성했습니다.

해결 과제

저장한 장소를 표시할 때마다 서버 응답을 기다리지 않으면서, 다른 기기에서 바뀐 정보와 삭제 내역도 반영해야 했습니다. 계정이 바뀌면 이전 계정의 로컬 데이터도 구분해야 했습니다.

설계 판단

Room에 저장한 장소의 복제본을 두고 화면을 먼저 구성했습니다. 수정 시각 이후의 변경분과 별도 삭제 내역을 합치고, 복제본의 소유 계정과 동기화 진행 상태를 함께 관리했습니다.

상세 구현 · 저장한 장소의 로컬 복제본과 증분 동기화
  1. 저장된 핀 먼저 표시Room의 장소 목록으로 지도를 먼저 구성하고, 세션 내 중복 동기화 요청을 막습니다.
  2. 변경 내역 합치기수정 시각 이후의 항목을 추가·갱신하고, 별도 삭제 내역으로 해제된 핀을 제거합니다.
  3. 계정과 커서 확인소유 계정이 바뀌면 로컬 데이터를 비우고, 커서가 전진하지 않는 응답은 반복 조회를 멈춥니다.

프로필의 장소 지도에서는 확대 수준과 화면에 보이는 타일을 기준으로 요청 순서를 정했습니다. 중간 확대 구간은 보이는 상세 타일부터 가져오고 넓은 영역 조회는 뒤로 미뤘습니다. 타일별 데이터 유무와 요청 상태를 공유해 빈 영역과 중복 요청을 건너뛰었습니다.

설계 비용 먼저 보여준 로컬 데이터와 서버 상태는 동기화 전까지 다를 수 있습니다. 추가·수정뿐 아니라 삭제 내역과 계정 전환까지 별도로 다뤄야 했습니다.

09 · TYPED GRAPHQL

요청과 응답의 계약을 타입으로 연결

문자열 쿼리와 수동 응답 처리를 생성된 GraphQL 타입에 맞춘 API 호출로 전환했습니다. 요청 변수와 응답 타입을 함께 연결하고, 목록 데이터와 페이지 커서를 분리했습니다.

해결 과제

쿼리와 응답 모델을 따로 관리하면 필드 변경이 화면까지 전달되는 과정에서 불일치가 생길 수 있습니다. 목록을 갱신할 때 다음 페이지의 커서를 함께 잃지 않도록 관리할 필요도 있었습니다.

설계 판단

생성된 Operation에 Variables·Data 타입을 묶어 API와 검색 호출에 적용했습니다. 페이지 응답의 행과 커서는 별도 상태로 보관해, 항목 교체와 추가 로딩을 독립적으로 처리했습니다.

상세 구현 · 타입 연결, 오류 처리, 페이지 응답
기존 호출 구조문자열 쿼리 + 변수 구성 → 수동 응답 해석
타입을 연결한 호출 구조Api.query(Operation<Variables, Data>, Variables) → Data

호출 단위의 타입

Operation이 변수와 결과의 직렬화 정보를 제공하도록 연결하고, 생성된 Fragment 타입을 화면 모델에 활용했습니다.

실패 경로 구분

HTTP 인증 실패, GraphQL 오류, 앱 업데이트 요구를 공통 통신 계층에서 구분해 처리했습니다.

페이지 응답 분리

행 목록과 next·prev 커서를 분리했습니다. 개별 항목을 교체해도 서버가 내려준 페이지 커서를 유지했습니다.

알 수 없는 enum 값의 보존, null 변수의 생략, 응답의 페이지 커서 처리를 확인하는 테스트를 추가했습니다.

설계 비용 스키마와 생성 코드를 함께 관리해야 합니다. 타입 검사로 구조의 불일치를 줄이면서도, 인증·서버 오류와 예상하지 못한 응답 값은 실행 시점에 별도로 처리했습니다.

10 · VERIFICATION & REVIEW

동작 확인과 구현 검토

직접 사용하며 확인한 범위

홈 스크롤은 Android Studio의 디버그 trace로 분석하고 릴리스 빌드에서 육안으로 확인했습니다. 화면 크기를 고려한 UI는 에뮬레이터에서 직접 실행해 이상 여부를 확인했습니다.

단위 테스트에 담은 경계 조건

복원 시 항목 수가 줄었을 때의 인덱스 보정, 페이지 선택·위치 상태, 다음 페이지 요청 조건을 테스트 코드에 담았습니다. GraphQL에서는 알 수 없는 enum, null 변수와 페이지 커서 처리를 다뤘습니다.

AI 구현에서 반복된 상태 소유권 문제

AI가 생성한 구현에서 핵심 기능·탭의 Store와 페이지 단위 ViewModel의 책임이 섞이는 문제가 반복됐습니다. 상태 소유권과 화면 이동 규칙을 CLAUDE.md에 명문화하고, 생성 결과를 해당 기준으로 검토·수정했습니다.

검토 기준 · 상태 소유권과 화면 이동

탭·공유 기능의 상태는 Store, 페이지 상태는 ViewModel에 두는 규칙을 CLAUDE.md에 기록했습니다. 화면 효과는 Composition의 수명에 맞춰 관리하도록 했습니다.

탭 상태     → Store
상세 상태   → ViewModel
화면 효과   → Composition

생성된 구현이 기존 설계와 맞는지 판단할 때 다음 지점을 살폈습니다.

  • 상태의 소유자와 정리 시점
  • 코루틴의 취소·중복 요청 처리
  • 컴포넌트가 연결되는 화면 이동과 사용자 흐름

상태가 유지되어야 할 범위를 먼저 정하고, 반복 작업이 실제로 발생하는 구간에 변경을 집중했습니다. 홈 스크롤의 TextStyle 캐시를 다시 제거한 경험처럼, 추가한 최적화도 유지 비용과 필요성을 다시 검토했습니다.
