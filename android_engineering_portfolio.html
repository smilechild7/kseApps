01 · CONTEXT & CONTRIBUTIONS

전환 배경과 맡은 일

전환의 배경

사진 편집과 화면 전환이 끊김 없이 이어지는 매끄러운 사용성을 목표로 했습니다. 자르기·회전과 제스처 반응을 세밀하게 조정하고, 데이터 미리보기는 멀티스레드를 활용해 반응성을 개선할 필요가 있었습니다. 이미지 처리와 백그라운드 작업, 화면 갱신을 Android에 맞게 직접 제어할 수 있도록 Kotlin·Jetpack Compose로 앱을 전체 재구현했습니다.

Android 개발 전담

Android 앱의 전체 재구현을 맡아 화면과 기능부터 탐색 구조, 상태 관리, API·로컬 데이터 흐름까지 설계하고 구현했습니다. 사진 편집·뷰어·업로드, 사진 기반 장소 추천과 방문 넛지, 지도 동기화를 개발하고, 탭별 상태 유지와 홈 스크롤 성능 개선까지 진행했습니다. UI 디자인 단계에도 참여해 뒤로가기·시스템 영역·폴더블 화면 등 Android에서 고려할 요구사항을 구현에 반영했습니다.

02 · HOMESCREEN SCROLL PERFORMANCE

홈 스크롤의 병목을 나누어 개선

HomeScreen은 LazyColumn 안에 여러 LazyRow가 중첩된 구조였습니다. 세로로 빠르게 스크롤하면 새 LazyRow의 사진 카드들이 한꺼번에 구성되면서 이미지 초기화와 측정 작업이 몰렸고, 화면이 끊겨 보였습니다.

화면 구조 LazyColumn → 섹션별 LazyRow·HorizontalPager → 사진 카드

문제

새로 들어오는 LazyRow의 카드 처리에 스크롤을 따라 움직이는 상단 영역(헤더)의 위치 갱신까지 겹쳤습니다. 새 카드를 준비하는 작업과 스크롤 중 계속 반복되는 작업을 나눠 살펴봤습니다.

구현 과정

내용이 바뀌지 않은 부분을 다시 계산하는 일부터 줄이고, 이미지 표시를 준비하는 과정과 카드 구조를 단순화했습니다. 헤더 위치를 갱신하는 방식도 바꿔, 스크롤 입력마다 처리할 작업이 쌓이지 않도록 했습니다.

확인 방법

Android Studio에서 디버그 빌드의 trace를 캡처해 스크롤 중 시간이 많이 걸리는 구간을 확인했습니다. 변경 후에는 릴리스 빌드를 직접 사용하면서 스크롤이 끊기는지 확인했습니다.

개선 과정
  1. 01

    스크롤할 때 다시 계산하는 화면 범위 줄이기

    스크롤 위치를 화면 구성 단계에서 읽으면, 위치가 바뀔 때마다 내용이 그대로인 부분도 다시 계산할 수 있었습니다. 위치값은 실제 배치·그리기 단계(offset·graphicsLayer)에서 읽도록 옮겼습니다. 목록도 데이터가 바뀔 때만 다시 만들도록 remember로 재사용했습니다.

  2. 02

    새 사진 카드마다 반복되는 이미지 준비 작업 줄이기

    여러 사진 카드가 한꺼번에 나타나면, 카드마다 이미지 표시 컴포넌트를 초기화하는 비용이 쌓였습니다. Coil 로더를 직접 호출해 결과 이미지를 그리는 FastAsyncImage를 만들어 표시 준비 과정을 줄였습니다. 기존 로더와 캐시는 그대로 공유했습니다.

  3. 03

    카드 크기와 배치를 계산하는 작업 줄이기

    사진 카드를 여러 레이아웃으로 감싸면서 크기와 위치를 계산해야 할 요소가 늘어났습니다. 불필요한 감싸기 구조를 제거하고 간격은 padding 등으로 처리했습니다. 목록에는 항목 유형(contentType)을 지정해 같은 구조의 카드와 섹션을 재사용할 수 있도록 했습니다.

  4. 04

    헤더 처리가 스크롤 입력을 지연시키지 않도록 변경

    스크롤을 따라 움직이는 헤더의 위치를 갱신하려고 입력마다 코루틴을 실행하면서 대기 작업이 쌓였습니다. 짧은 위치 갱신은 입력을 처리할 때 바로 반영하도록 바꿨습니다. 손을 뗀 뒤 본문이 움직이는 관성 스크롤도 헤더 애니메이션을 기다리지 않도록 분리했습니다.

이미지 표시의 적용 범위 홈 카드에 필요한 비트맵 표시를 지원하고, 사진 전환 효과(crossfade)와 범용 오류 이미지는 생략했습니다. 이런 기능이 필요한 다른 화면에서는 기존 이미지 컴포넌트를 유지했습니다.

03 · NAVIGATION & STATE

4개의 NavController로 탭별 상태 유지

홈·지도·타임라인·마이 탭에 NavController를 각각 두고, 탭마다 독립된 백스택을 유지했습니다. 다른 탭을 다녀와도 보던 상세 화면과 목록 위치가 남도록 하고, 지도는 같은 인스턴스를 유지해 카메라 위치와 선택한 장소를 이어서 보여줬습니다.

문제

각 탭에서 상세 화면을 열어둔 채 다른 탭을 다녀와도, 보던 화면과 탐색 위치가 남아 있어야 했습니다. 지도 역시 탭 전환 때 다시 로딩되거나 카메라 위치가 초기화되면 탐색이 끊겼습니다.

구현 과정

탭별로 NavController와 NavHost를 만들고, 네 NavHost를 Composition에 유지했습니다. 탭을 바꿀 때는 기존 백스택을 그대로 둔 채 zIndex와 활성 상태로 보이는 탭을 바꿨습니다. 공통 상세 화면은 commonNavGraph()로 각 탭에 등록해, 어느 탭에서 열었든 그 탭의 이동 이력에 쌓이게 했습니다.

상세 구현 · 탭·페이지 상태와 작업의 수명

탭에서 함께 쓰는 상태는 Store에, 상세 화면의 상태는 해당 백스택 항목의 ViewModel에 뒀습니다. 상태 변경은 Store·ViewModel의 함수로 모으고 UI에는 읽기 전용 StateFlow를 전달했습니다. 로그인·글쓰기 진입은 별도의 rootNavController로, 글쓰기 내부 이동은 writeNavController로 처리했습니다.

목록·그리드·페이저의 위치는 섹션별 키로 구분해 스크롤이 멈출 때 저장했습니다. 다시 열었을 때 항목 수가 줄어들 수 있어, 복원할 인덱스를 현재 목록 크기에 맞췄습니다. 무한 반복 페이저는 실제 콘텐츠의 페이지를 저장해 복원했습니다.

고려한 점 네 탭과 지도를 계속 유지하는 만큼 메모리 사용과 비활성 탭의 동작을 함께 관리해야 했습니다. 숨겨진 탭은 포커스와 접근성 탐색에서 제외하고, 뒤로가기는 현재 보이는 탭이 처리하도록 했습니다. 전역 Store를 테스트에서 다른 구현으로 바꾸기 어려운 점도 남았습니다.

04 · PHOTO EDITING & LIFECYCLE

사진 편집부터 복원·뷰어·업로드까지

사진을 자르고 회전·반전하는 편집 기능과 전체화면 뷰어를 만들었습니다. 글쓰기를 다시 열어도 편집을 이어갈 수 있도록 원본과 편집 정보를 저장하고, 업로드 후 파일을 정리하는 과정까지 연결했습니다.

01편집원본 좌표와 결과 이미지02상태 복원원본·편집 정보 보존03뷰어제스처와 화면 전환04업로드·파일 관리변경분 전송과 참조 정리
  1. 01

    편집 · 화면에서 본 영역을 결과 이미지로

    회전 정보가 있는 사진은 화면에서 고른 영역을 그대로 잘라도 원본 픽셀 좌표와 맞지 않을 수 있었습니다. 먼저 사진의 회전 메타데이터를 반영하고, 화면의 자르기 영역을 원본 픽셀 좌표로 바꾼 뒤 편집을 적용했습니다.

    상세 구현 · 좌표 변환과 편집 결과

    자유 비율과 1:1·3:4·4:3·9:16·16:9 등의 고정 비율을 지원했습니다. 자르기 영역은 이미지 경계 안으로 제한하고, 90도 회전 시에는 가로·세로 비율과 반전 축을 함께 보정했습니다.

    결과 이미지 생성 순서원본 회전 반영 → 화면의 자르기 좌표를 픽셀로 변환 → 자르기 → 사용자 반전·회전 적용

    비트맵을 만들고 파일에 저장하는 작업은 IO로 분리했습니다. 편집본은 별도 파일에 저장하고, 다시 편집할 때 사용할 원본도 함께 보관했습니다.

  2. 02

    상태 복원 · 앨범을 옮기고 다시 열어도 이어서

    앨범을 바꾸거나 사진 목록을 갱신하면 편집한 사진이 원본으로 돌아가는 문제가 있었습니다. 사진 ID를 기준으로 목록과 선택 상태에 편집 결과를 같이 반영했습니다. 임시저장에는 원본·편집본 URI와 편집 정보도 넣었습니다.

    상세 구현 · 원본 보존과 재편집

    편집본의 치수·회전 정보와 자르기 영역·반전·선택 비율을 저장했습니다. 다시 편집할 때는 원본을 열고 이 정보를 적용했습니다. 이미 잘린 사진을 계속 자르면서 화질이나 편집 가능한 영역이 줄어들지 않도록 한 방식입니다.

    화면 크기가 바뀌어도 자르기 영역을 복원할 수 있도록 이전 영역을 이미지 기준의 상대 좌표로 바꾼 뒤, 새 화면에 맞춰 다시 계산했습니다. 기기 사진 목록을 인덱싱된 목록으로 바꿀 때도 선택한 편집본 URI를 유지했습니다.

  3. 03

    뷰어 · 확대·넘김·닫기를 상태에 따라 구분

    기본 배율에서는 좌우 넘김과 수직 드래그 닫기를, 확대 상태에서는 사진 내부 이동을 처리했습니다. 손가락 중심을 기준으로 확대하고, 손을 뗐을 때의 관성과 경계 복귀를 X·Y축별로 관리했습니다.

    상세 구현 · 제스처와 화면 전환

    확대와 경계 저항

    핀치와 더블탭으로 확대하고, 손을 떼면 1–3배 범위로 복귀하도록 했습니다. 입력값과 표시값을 분리해 경계 저항이 반복 적용되는 떨림을 막았습니다.

    축별 관성

    축마다 Animatable을 두어 한 축이 경계에 닿아도 다른 축은 감속을 이어가게 했습니다. 새 터치가 시작되면 진행 중인 관성을 멈췄습니다.

    열기와 닫기

    썸네일의 위치·크기에서 전체화면으로 펼쳤습니다. 닫기 버튼·뒤로가기는 원본 위치로 복귀하고, 수직 드래그 닫기는 화면 밖으로 이동하게 했습니다.

    Predictive Back 진행도에 따라 전환을 적용하고, 취소하면 스프링으로 복원했습니다. 원본 셀의 위치를 알 수 없는 사진은 페이드로 닫았습니다.

    고려한 점 확대된 사진을 움직이는 입력과 사진을 넘기거나 닫는 입력이 겹치지 않도록 우선순위를 정했습니다. Dialog를 안정적으로 닫기 위해 하드웨어 비트맵은 사용하지 않았고, 이 선택으로 메모리 사용량이 늘어날 수 있습니다.

  4. 04

    업로드·파일 관리 · 변경한 사진과 파일 수명 구분

    업로드 전 사진을 긴 변 기준 최대 2048px로 변환했습니다. 리뷰 수정에서는 기존 서버 사진과 새로 추가한 사진을 구분해 신규 사진만 업로드하고, 삭제한 사진은 ID 목록으로 전달했습니다.

    상세 구현 · 이미지 변환, 파일 정리, 갤러리 저장

    먼저 이미지 치수를 읽고 샘플링해 디코딩한 뒤, EXIF 회전과 리사이즈를 적용해 업로드용 JPEG를 생성했습니다. 변환용 임시 파일과 글쓰기의 편집본 파일은 별도로 관리했습니다.

    업로드 후 편집본을 정리할 때는 다른 임시저장 글에서 참조하는지 확인했습니다. 리뷰 수정이 끝나면 게시글을 다시 조회해 홈·타임라인·프로필에 결과를 반영했습니다.

    갤러리 저장은 Coil 디스크 캐시의 바이트를 우선 사용하고, 캐시를 사용할 수 없으면 비트맵을 JPEG로 변환했습니다. 저장 작업은 뷰어를 닫아도 이어지도록 앱 수명의 코루틴에서 실행했습니다.

05 · ANDROID UI & DEVICE ADAPTATION

화면 크기와 시스템 동작을 고려한 Android UI

UI 디자인 회의에서 Android의 뒤로가기와 시스템 내비게이션 바를 고려해 달라고 요청했습니다. 폴더블처럼 화면이 넓어져도 자연스럽게 보이도록 이야기하고, 화면 폭에 따른 배치와 크기 제한을 구현했습니다.

01

넓어져도 과도하게 커지지 않게

화면 폭을 구간별로 나누어 배치를 바꾸고, 크기가 달라지면 화면 정보를 갱신했습니다. 넓은 화면에서 홈 페이저의 카드가 너무 커지지 않도록 폭을 제한하고, 사진과 배너의 확대 비율에도 상한을 뒀습니다.

02

시스템 영역과 콘텐츠의 경계

하단 탭에는 시스템 내비게이션 바 높이를 더하고, 편집·입력 화면에는 내비게이션 바와 키보드 인셋을 적용했습니다. 지도 탭의 기본 화면에서는 뒤로가기로 검색을 먼저 닫도록 했습니다.

03

에뮬레이터에서 직접 확인

화면 폭에 맞춰 배치를 바꾼 뒤 에뮬레이터에서 앱을 직접 실행했습니다. 폴더블을 고려해 수정한 UI가 이상 없이 동작하는지 확인했습니다.

06 · RECENT-PHOTO VISIT NUDGE

최근 사진에서 시작되는 방문 넛지

기기의 최근 사진을 보고 “이 장소에 다녀오셨나요?”라고 묻는 넛지를 만들었습니다. 사진과 위치 메타데이터 접근 권한을 먼저 확인하고, 음식 분류는 기기에서 처리했습니다. 주변 장소를 찾을 때는 방문 묶음의 대표 좌표를 서버에 전달했습니다.

문제

방문 사진을 찍어도 리뷰를 남기려면 직접 글쓰기를 열고 장소를 찾아야 했습니다. 최근 사진에서 방문한 곳을 추정해 앱이 먼저 방문 여부를 묻고, 리뷰 작성을 제안하도록 했습니다.

구현 과정

로그인 상태에서 필요한 권한이 있으면 최근 사진을 확인했습니다. 비슷한 시간과 위치에서 찍힌 사진을 한 번의 방문으로 묶고, ML Kit의 음식 라벨에 주변 장소의 메뉴·업종·거리·촬영 당시 영업 여부를 함께 반영해 후보를 골랐습니다.

사진과 장소 후보를 팝업으로 보여주고, 다른 장소를 고르거나 닫을 수 있게 했습니다.

상세 구현 · 방문 묶음, 음식 분류, 후보 정렬
  1. 방문 단위로 묶기최근 24시간의 사진 중 위치가 있는 사진을 추리고, 30분·100m 기준으로 방문을 나눕니다.
  2. 음식 라벨 추출방문마다 최대 5장의 사진을 기기에서 분류하고, 음식 관련 라벨과 신뢰도를 모읍니다.
  3. 주변 장소 비교묶음의 평균 좌표 주변을 조회하고, 라벨과 메뉴·업종의 일치 정도에 거리·영업시간을 반영합니다.

READ_MEDIA_IMAGES 등 해당 Android 버전의 사진 접근 권한과 ACCESS_MEDIA_LOCATION을 확인했습니다. Android 14 이상에서 선택한 사진에만 접근할 수 있는 경우에는 이 자동 분석을 건너뛰었습니다. 최근 24시간의 사진을 프로세스당 한 번 백그라운드에서 확인하고, 사진 수와 장소 조회 횟수를 제한하며 연속 조회 실패 시 중단했습니다.

영업시간 정보가 없는 장소는 점수를 그대로 두고, 촬영 시각에 영업하지 않았던 장소는 점수를 낮췄습니다.

고려한 점 GPS와 음식 분류 결과만으로 장소를 정확히 고르기는 어려웠습니다. 다른 후보를 직접 선택할 수 있게 하고, 위치 정보가 없는 사진은 분석에서 제외했습니다.

07 · PHOTO & PLACE COMPOSING

사진과 장소를 연결하는 글쓰기

글쓰기에서 사진을 고르면 촬영 위치 주변의 장소를 추천하고, 장소를 고르면 ‘장소 주변 사진’ 앨범을 보여주게 했습니다. 사진과 장소 중 무엇을 먼저 골라도 다음 선택에 활용할 수 있도록 만들었습니다.

문제

사진을 첨부한 뒤에는 장소를 다시 검색해야 했습니다. 장소부터 고르면 촬영 날짜를 떠올리며 갤러리를 찾아야 했습니다. 이미 선택한 사진이나 장소를 이용해 이 과정을 줄이고 싶었습니다.

구현 과정

사진을 먼저 고르면 GPS 좌표로 주변 장소를 조회해 추천 칩을 보여줬습니다. 장소를 먼저 고르면 Room에 미리 저장한 사진의 EXIF 위치를 조회해 주변 사진 앨범을 만들었습니다.

추천 장소를 바로 선택하거나 별도 장소 검색으로 이어갈 수 있게 하고, 기준 좌표가 달라질 때 추천을 갱신했습니다.

상세 구현 · 백그라운드 인덱싱과 좌표 검색
  1. MediaStore기기 사진 목록과 ID를 확인합니다.
  2. EXIF → Room위치 메타데이터를 로컬 데이터베이스에 저장합니다.
  3. 좌표 범위 쿼리선택한 장소 주변의 후보 사진을 조회합니다.

장소 주변 사진을 찾을 때는 위·경도에 각각 오프셋을 적용한 사각 범위로 조회했습니다. 매번 사진의 EXIF를 읽지 않도록 위치 정보를 Room에 저장하고, WorkManager로 새로 생기거나 삭제된 사진을 반영했습니다.

사진에서 장소를 찾을 때는 선택한 사진들 중 첫 GPS 좌표를 서버 검색에 전달했습니다. 기준 좌표가 달라지면 장소 후보도 다시 가져왔습니다.

남은 한계 처음에는 사진을 읽어 위치 인덱스를 만드는 시간이 필요했습니다. 접근 권한이나 GPS가 없는 사진은 후보에 넣지 못했습니다. 신규·삭제 ID를 기준으로 동기화해, 기존 사진의 메타데이터 수정까지 추적하지는 못했습니다.

선택한 사진의 편집·임시저장·업로드 과정은 사진 편집부터 복원·뷰어·업로드까지에 정리했습니다.

08 · MAP INTEGRATION & SYNC

저장한 장소를 로컬과 서버에서 일관되게

저장한 장소는 Room에서 먼저 읽어 지도에 표시하고, 서버의 추가·수정·삭제 내역을 받아 갱신했습니다. 장소 지도는 화면에 보이는 영역부터 요청하도록 순서를 정했습니다.

문제

지도를 열 때마다 서버 응답을 기다리게 하고 싶지는 않았습니다. 로컬에 저장한 장소를 먼저 보여주면서도, 다른 기기의 변경 사항과 삭제된 장소를 반영해야 했습니다. 계정이 바뀌었을 때 이전 계정의 데이터가 남지 않도록 처리할 필요도 있었습니다.

구현 과정

Room에 저장한 장소로 화면을 먼저 만들고, 마지막 수정 시각 이후의 변경분을 합쳤습니다. 삭제 내역은 따로 받아 반영했습니다. 로컬 데이터가 어느 계정에 속하는지와 동기화 진행 상태도 함께 관리했습니다.

상세 구현 · 저장한 장소의 로컬 복제본과 증분 동기화
  1. 저장된 핀 먼저 표시Room의 장소 목록으로 지도를 먼저 구성하고, 세션 내 중복 동기화 요청을 막습니다.
  2. 변경 내역 합치기수정 시각 이후의 항목을 추가·갱신하고, 별도 삭제 내역으로 해제된 핀을 제거합니다.
  3. 계정과 커서 확인소유 계정이 바뀌면 로컬 데이터를 비우고, 커서가 전진하지 않는 응답은 반복 조회를 멈춥니다.

프로필의 장소 지도는 확대 수준과 현재 보이는 타일을 보고 요청 순서를 정했습니다. 중간 확대 구간에서는 보이는 상세 타일부터 가져오고 넓은 영역 조회는 뒤로 미뤘습니다. 타일별 데이터 유무와 요청 상태를 공유해 빈 영역을 다시 조회하거나 같은 요청을 반복하지 않도록 했습니다.

고려한 점 로컬 데이터를 먼저 보여주기 때문에 동기화가 끝나기 전에는 서버와 내용이 다를 수 있습니다. 삭제된 핀이 남거나 계정 간 데이터가 섞이지 않도록 삭제 내역과 계정 전환도 따로 처리했습니다.

09 · TYPED GRAPHQL

GraphQL 요청과 응답을 타입으로 연결

문자열로 쿼리를 만들고 응답을 직접 해석하던 코드를 생성된 GraphQL 타입으로 바꿨습니다. 요청 변수와 응답 타입을 호출에 함께 묶고, 목록을 갱신해도 페이지 커서가 유지되도록 데이터와 커서를 나눴습니다.

문제

쿼리와 응답 모델을 따로 관리하면 필드를 바꿀 때 서로 어긋날 수 있었습니다. 목록 항목을 수정할 때 다음 페이지 커서까지 바뀌지 않도록 하는 처리도 필요했습니다.

구현 과정

생성된 Operation에 Variables·Data 타입을 연결해 API와 검색에서 사용했습니다. 응답의 행 목록과 커서는 따로 저장해, 항목을 교체하는 작업과 다음 페이지를 가져오는 작업을 분리했습니다.

상세 구현 · 타입 연결, 오류 처리, 페이지 응답
기존 호출 구조문자열 쿼리 + 변수 구성 → 수동 응답 해석
타입을 연결한 호출 구조Api.query(Operation<Variables, Data>, Variables) → Data

호출 단위의 타입

Operation이 변수와 결과의 직렬화 정보를 제공하도록 연결하고, 생성된 Fragment 타입을 화면 모델에 활용했습니다.

실패 경로 구분

HTTP 인증 실패, GraphQL 오류, 앱 업데이트 요구를 공통 통신 계층에서 구분해 처리했습니다.

페이지 응답 분리

행 목록과 next·prev 커서를 분리했습니다. 개별 항목을 교체해도 서버가 내려준 페이지 커서를 유지했습니다.

알 수 없는 enum 값의 보존, null 변수의 생략, 응답의 페이지 커서 처리를 확인하는 테스트를 추가했습니다.

고려한 점 타입을 연결한 뒤에는 스키마와 생성 코드도 함께 맞춰야 했습니다. 인증 실패나 서버 오류, 예상하지 못한 응답 값은 실행 중에 발생하므로 별도로 처리했습니다.

10 · VERIFICATION & REVIEW

직접 확인하고 코드를 검토한 과정

직접 실행해 본 부분

홈 스크롤은 릴리스 빌드에서 직접 사용해 보고, 화면 크기에 따른 UI는 에뮬레이터에서 확인했습니다. 확인한 내용은 각 구현 과정에 함께 정리했습니다.

테스트로 확인하려고 한 상황

목록이 줄어든 뒤 위치를 복원하는 경우, 선택한 페이지와 스크롤 위치를 유지하는 경우, 다음 페이지를 요청하는 조건에 대해 테스트를 작성했습니다. GraphQL은 알 수 없는 enum, null 변수 생략, 페이지 커서 처리를 테스트에 넣었습니다.

AI가 Store와 ViewModel의 역할을 섞을 때

AI에 구현을 맡기면 탭·공유 기능의 Store와 페이지 단위 ViewModel의 역할을 섞는 경우가 자주 있었습니다. 두 역할과 화면 이동 규칙을 CLAUDE.md에 정리하고, 생성된 코드가 이 구조를 따르는지 확인해 수정했습니다.

코드를 검토할 때 확인한 내용

여러 화면이나 탭에서 함께 쓰는 상태는 Store에, 페이지에서 쓰는 상태는 ViewModel에 두도록 정리했습니다. UI 작업은 Composition의 수명에 맞춰 관리하게 했습니다.

탭·공유 상태 → Store
페이지 상태  → ViewModel
화면 효과    → Composition

생성된 코드를 합치기 전에 상태를 어디에 두었는지, 화면을 옮겨도 작업이 의도한 대로 이어지거나 정리되는지 살폈습니다.

  • 상태의 소유자와 정리 시점
  • 코루틴의 취소·중복 요청 처리
  • 컴포넌트가 연결되는 화면 이동과 사용자 흐름
