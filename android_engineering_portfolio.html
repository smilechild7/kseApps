02 · NAVIGATION & STATE

탭을 이동해도 탐색은 이어지도록

탭별 백스택과 지도 인스턴스를 분리해 유지했습니다. 상세 화면에서 돌아왔을 때 이전 장소와 탐색 위치를 다시 보여주도록 연결했습니다.

해결 과제

탭 이동이나 상세 화면 진입 때문에 지도와 목록이 초기화되면, 사용자는 방금 보던 장소를 다시 찾아야 했습니다.

설계 판단

화면의 이동 이력과 지도 View의 수명을 분리했습니다. 공통 상세 라우트는 재사용하면서 각 탭이 자신의 백스택을 갖게 하고, 지도는 NavHost 바깥에서 유지했습니다.

상세 구현 · 상태와 작업의 수명

탭 상태 · Store

목록과 지도 상태는 Store가 소유하고, 데이터 로딩은 Store의 CoroutineScope에서 이어가게 했습니다.

상세 상태 · ViewModel

상세마다 백스택 단위 ViewModel을 두고, 항목이 제거되면 해당 요청도 함께 정리되도록 했습니다.

화면 효과 · Composition

UI에 종속된 작업은 LaunchedEffect에 배치했습니다. 비활성 탭의 컴포지션을 유지하는 경우에는 가시성도 별도로 다뤘습니다.

상태 변경은 Store·ViewModel의 함수로 모으고, UI에는 읽기 전용 StateFlow를 노출했습니다. 글쓰기는 루트에서 모달로 진입하는 별도 흐름으로 구성했습니다.

목록·그리드·페이저의 위치는 섹션별 키로 저장했습니다. 스크롤이 멈춘 시점에 위치를 기록하고, 복원할 때는 달라진 항목 수에 맞춰 인덱스를 보정했습니다. 무한 반복 페이저는 내부 인덱스 대신 실제 콘텐츠의 페이지를 기준으로 복원했습니다.

설계 비용 지도와 백스택을 따로 유지하는 만큼 뒤로가기·시트 복원·가시성 관리가 복잡해졌습니다. 전역 Store는 테스트에서 교체하기 어렵다는 점도 남았습니다.

03 · RECENT-PHOTO VISIT NUDGE

최근 사진에서 시작되는 방문 넛지

앱이 기기의 최근 사진을 확인하고 방문 장소를 추정해, 방문 여부를 묻고 리뷰 작성을 제안하는 넛지를 구현했습니다. 사진의 촬영 위치·시각과 음식 분류 결과를 함께 활용했습니다.

해결 과제

방문 사진을 찍은 뒤에도 리뷰를 쓰려면 사용자가 직접 글쓰기를 시작하고 장소를 찾아야 했습니다. 최근 사진을 단서로 앱이 먼저 방문을 묻고, 기록을 시작할 계기를 제공하고자 했습니다.

설계 판단

로그인 상태에서 최근 사진을 자동으로 확인하고, 비슷한 시간과 위치에서 찍힌 사진을 하나의 방문으로 묶었습니다. ML Kit의 음식 라벨에 주변 장소의 메뉴·업종·거리·촬영 당시 영업 여부를 조합해 후보를 정했습니다.

추정한 장소를 사진과 함께 팝업으로 제안하고, 사용자가 다른 후보를 고르거나 닫을 수 있도록 했습니다.

상세 구현 · 방문 묶음, 음식 분류, 후보 정렬
  1. 방문 단위로 묶기최근 24시간의 사진 중 위치가 있는 사진을 추리고, 30분·100m 기준으로 방문을 나눕니다.
  2. 음식 라벨 추출방문마다 최대 5장의 사진을 기기에서 분류하고, 음식 관련 라벨과 신뢰도를 모읍니다.
  3. 주변 장소 비교묶음의 평균 좌표 주변을 조회하고, 라벨과 메뉴·업종의 일치 정도에 거리·영업시간을 반영합니다.

로그인 상태 진입 시 사진 접근과 위치 메타데이터 접근 권한을 확인하고, 최근 24시간에 촬영한 사진을 프로세스당 한 번 백그라운드에서 조회·분석하도록 구성했습니다. 분석할 사진 수를 제한하고, 조회가 연속으로 실패하면 중단하도록 했습니다.

사진 분류는 기기에서 수행하고, 주변 장소를 찾을 때는 방문 묶음의 대표 좌표를 서버 검색에 전달했습니다. 영업시간 정보가 없으면 중립적으로 처리하고, 촬영 시각에 닫힌 장소에는 감점을 적용했습니다.

설계 비용 GPS 오차와 음식 분류의 모호함 때문에 한 장소를 단정하기 어렵습니다. 여러 후보와 선택 UI를 함께 제공하고, 사진 위치 정보가 없는 경우는 분석 대상에서 제외했습니다.

04 · PHOTO & PLACE COMPOSING

사진과 장소를 연결하는 글쓰기

글쓰기에서 사진을 고르면 촬영 위치 주변의 장소를 추천하고, 장소를 고르면 ‘장소 주변 사진’ 앨범을 보여주도록 구현했습니다. 사용자가 어느 쪽부터 선택하든 작성 흐름을 이어갈 수 있게 했습니다.

해결 과제

사진을 첨부한 뒤 장소를 다시 검색하거나, 장소를 고른 뒤 갤러리에서 촬영 날짜를 떠올리며 사진을 찾아야 했습니다. 먼저 선택한 정보로 다음 선택을 도울 필요가 있었습니다.

설계 판단

사진에서 시작할 때는 선택한 사진의 GPS로 주변 장소를 조회해 추천 칩을 보여줬습니다. 장소에서 시작할 때는 미리 인덱싱한 EXIF 위치를 Room에서 조회해 관련 사진 앨범을 구성했습니다.

추천 장소를 바로 선택하거나 별도 장소 검색으로 이어갈 수 있게 하고, 기준 좌표가 달라질 때 추천을 갱신했습니다.

상세 구현 · 백그라운드 인덱싱과 좌표 검색
  1. MediaStore기기 사진 목록과 ID를 확인합니다.
  2. EXIF → Room위치 메타데이터를 로컬 데이터베이스에 저장합니다.
  3. 좌표 범위 쿼리선택한 장소 주변의 후보 사진을 조회합니다.

위·경도에 서로 다른 오프셋을 적용한 사각 범위로 후보를 추렸습니다. 사진 메타데이터는 Room에 인덱싱해 기기 안에서 조회하고, WorkManager로 신규·삭제 사진을 반영했습니다.

반대 방향의 글쓰기 흐름에서는 선택한 사진 중 첫 GPS 좌표를 서버 검색에 전달해 주변 장소 후보를 보여줬습니다. 사진을 고른 뒤 장소를 붙이거나, 장소를 고른 뒤 관련 사진을 찾는 흐름을 모두 지원했습니다.

설계 비용 초기 인덱싱에는 시간이 필요하고, 위치 권한이나 GPS가 없는 사진은 후보에서 빠집니다. 사각 범위 검색은 원형 반경과 차이가 있으며, 신규·삭제 ID 중심 동기화는 기존 사진의 메타데이터 수정까지 추적하지 않습니다.

상세 구현 · 사진 편집, 임시저장, 리뷰 수정

편집 상태 복원

원본·편집본 URI와 자르기·회전·반전 정보를 임시저장에 함께 기록해, 글쓰기를 다시 열어도 편집을 이어가도록 했습니다.

변경분만 업로드

리뷰 수정 시 기존 서버 사진은 유지하고 새로 추가한 사진만 업로드했습니다. 삭제한 사진은 ID 목록으로 구분했습니다.

화면 간 결과 반영

수정 완료 후 게시글을 다시 조회해 홈·타임라인·프로필의 내용을 갱신했습니다. 임시 파일은 다른 초안의 참조 여부를 확인한 뒤 정리했습니다.

05 · GESTURE & MOTION

손가락 입력과 화면의 움직임을 분리

사진 확대·이동·페이지 전환·닫기를 하나의 뷰어에 통합했습니다. 원본 셀과 전체화면 사이의 전환, 축별 관성, Predictive Back까지 연결했습니다.

해결 과제

같은 입력이 확대·페이지 이동·닫기로 겹쳐 해석됐습니다. 경계 저항을 반복 적용하면 손을 멈춰도 떨리고, 두 축의 관성을 묶으면 한 축의 충돌이 다른 축까지 멈추게 했습니다.

설계 판단

원본 입력은 그대로 누적하고 표시할 배율만 따로 계산했습니다. X·Y축 관성은 각각 관리하고, 배율과 포인터 수에 따라 제스처를 소비하는 계층을 나눴습니다.

상세 구현 · 입력 계층, 관성, 화면 전환

입력 계층

확대 상태와 멀티 터치는 안쪽 Pinch/Pan, 기본 배율의 수평 이동은 HorizontalPager, 수직 드래그는 바깥 닫기 계층이 담당하게 했습니다.

축별 관성

하나의 Animatable<Offset> 대신 축마다 Animatable<Float>를 사용해, 한 축이 경계에 닿아도 다른 축은 감속을 이어가게 했습니다.

전환과 복귀

원본 셀의 위치·크기와 전체화면 영역을 보간했습니다. Predictive Back 진행도를 같은 전환에 연결하고, 취소 시에는 스프링으로 복원했습니다.

설계 비용 제스처와 애니메이션의 조합이 복잡해져 상태와 렌더링을 나눌 필요가 있습니다. Dialog 해제 안정성을 위해 하드웨어 비트맵을 피한 선택은 메모리 비용을 늘릴 수 있습니다.

06 · FEED RENDERING

가장 자주 반복되는 이미지 경로에 집중

피드 전용 경량 이미지 경로와 LazyList 재사용 정책을 적용했습니다. Coil 로더와 캐시는 공유하고, 상세 화면에서는 범용 이미지 컴포넌트를 유지했습니다.

해결 과제

빠른 스크롤 중 이미지 카드가 새로 등장할 때 끊김이 나타났습니다. 다운로드뿐 아니라 Composition 진입 시 반복되는 이미지 셋업과 객체 생성도 살펴봤습니다.

설계 판단

피드에서 사용하지 않는 표현 기능을 덜어내고 ImageLoader.execute()로 비트맵을 받아 표시했습니다. 고정 스타일은 재사용하고, 목록에는 항목 ID와 구조에 맞는 key·contentType을 지정했습니다.

상세 구현 · 진단 범위와 경량 경로

사진이 많은 카드가 연속으로 등장하는 구간에 집중해 이미지 초기화, 스타일 객체 생성, 항목 재활용을 조사했습니다. 정적인 TextStyle·Brush는 파일 수준에서 재사용하고, 입력에 따라 바뀌는 계산에는 remember(key)를 사용했습니다.

상세 화면AsyncImage → Coil ImageLoader
피드 썸네일LaunchedEffect(uri) → execute() → Image(bitmap)

타임라인에는 목록 끝 근처에서 다음 페이지를 요청하는 추가 로딩을 연결했습니다.

설계 비용 피드 전용 경로에서는 crossfade·error painter 등 범용 기능을 생략하고 비트맵 Drawable을 전제로 했습니다. 그래서 적용 범위를 피드 썸네일로 한정했습니다.

07 · MAP INTEGRATION & SYNC

지도 탐색과 저장한 장소를 일관되게

카메라 이동의 원인을 구분해 ‘이 지역 재검색’을 표시했습니다. 저장한 장소는 로컬 데이터로 먼저 보여주고, 서버의 추가·수정·삭제 내역을 동기화했습니다.

해결 과제

Compose 상태 변화와 SDK의 명령·콜백을 그대로 연결하면, 검색에 의한 카메라 이동까지 사용자 제스처로 처리할 수 있었습니다.

설계 판단

지속되는 속성은 StateFlow, 이동·핀 변경 같은 작업은 MapCommand, 사용자 조작은 SDK 이벤트로 분리했습니다. 카메라 변경 이유와 Idle 시점을 함께 확인했습니다.

상세 구현 · 상태, 명령, 이벤트
  1. 상태Store의 상태를 AndroidView의 속성에 반영합니다.
  2. 명령MapScreen에서 카메라 이동과 핀 조작을 수행합니다.
  3. 이벤트SDK 콜백의 이유를 구분해 Store와 UI를 갱신합니다.

설계 비용 Activity 수명주기와 탭 가시성을 함께 관리해야 했습니다. replay=0인 SharedFlow는 구독 전 명령을 보관하지 않으므로, SDK 준비 상태에 따른 명령 보류·재전달은 보완할 지점입니다.

상세 구현 · 저장한 장소의 로컬 복제본과 증분 동기화
  1. 저장된 핀 먼저 표시Room의 장소 목록으로 지도를 먼저 구성하고, 세션 내 중복 동기화 요청을 막습니다.
  2. 변경 내역 합치기수정 시각 이후의 항목을 추가·갱신하고, 별도 삭제 내역으로 해제된 핀을 제거합니다.
  3. 계정과 커서 확인소유 계정이 바뀌면 로컬 데이터를 비우고, 커서가 전진하지 않는 응답은 반복 조회를 멈춥니다.

프로필의 장소 지도에서는 확대 수준과 화면에 보이는 타일을 기준으로 요청 순서를 정했습니다. 중간 확대 구간은 보이는 상세 타일부터 가져오고 넓은 영역 조회는 뒤로 미뤘습니다. 타일별 데이터 유무와 요청 상태를 공유해 빈 영역과 중복 요청을 건너뛰었습니다.

설계 비용 먼저 보여준 로컬 데이터와 서버 상태는 동기화 전까지 다를 수 있습니다. 추가·수정뿐 아니라 삭제 내역과 계정 전환까지 별도로 다뤄야 했습니다.

08 · TYPED GRAPHQL

요청과 응답의 계약을 타입으로 연결

문자열 쿼리와 수동 응답 처리를 생성된 GraphQL 타입에 맞춘 API 호출로 전환했습니다. 요청 변수와 응답 타입을 함께 연결하고, 목록 데이터와 페이지 커서를 분리했습니다.

해결 과제

쿼리와 응답 모델을 따로 관리하면 필드 변경이 화면까지 전달되는 과정에서 불일치가 생길 수 있습니다. 목록을 갱신할 때 다음 페이지의 커서를 함께 잃지 않도록 관리할 필요도 있었습니다.

설계 판단

생성된 Operation에 Variables·Data 타입을 묶어 API와 검색 호출에 적용했습니다. 페이지 응답의 행과 커서는 별도 상태로 보관해, 항목 교체와 추가 로딩을 독립적으로 처리했습니다.

상세 구현 · 타입 연결, 오류 처리, 페이지 응답
기존 호출 구조문자열 쿼리 + 변수 구성 → 수동 응답 해석
타입을 연결한 호출 구조Api.query(Operation<Variables, Data>, Variables) → Data

호출 단위의 타입

Operation이 변수와 결과의 직렬화 정보를 제공하도록 연결하고, 생성된 Fragment 타입을 화면 모델에 활용했습니다.

실패 경로 구분

HTTP 인증 실패, GraphQL 오류, 앱 업데이트 요구를 공통 통신 계층에서 구분해 처리했습니다.

페이지 응답 분리

행 목록과 next·prev 커서를 분리했습니다. 개별 항목을 교체해도 서버가 내려준 페이지 커서를 유지했습니다.

알 수 없는 enum 값의 보존, null 변수의 생략, 응답의 페이지 커서 처리를 확인하는 테스트를 추가했습니다.

설계 비용 스키마와 생성 코드를 함께 관리해야 합니다. 타입 검사로 구조의 불일치를 줄이면서도, 인증·서버 오류와 예상하지 못한 응답 값은 실행 시점에 별도로 처리했습니다.

09 · AI-ASSISTED DEVELOPMENT

작업을 나누고, 설계 기준은 함께 공유

Claude로 분리 가능한 작업을 병렬로 진행하고, 상태 소유권과 개발 규칙을 지침으로 공유했습니다. 구현 방향을 정하고 결과를 프로젝트에 통합하는 역할은 직접 맡았습니다.

해결 과제

여러 영역을 동시에 수정하면 컴포넌트마다 상태를 저장하는 위치나 비동기 작업의 수명이 달라질 수 있었습니다.

설계 판단

구현 전에 변경 범위와 공통 규칙을 정리했습니다. 화면·로직 작업을 나누더라도 기존 Store·ViewModel 구조와 사용자 흐름을 기준으로 결과를 검토했습니다.

상세 구현 · 공유한 기준

탭과 함께 유지할 정보는 Store, 상세 화면에 종속된 정보는 백스택 ViewModel, UI 효과는 Composition에 배치하는 기준을 공유했습니다.

탭 상태     → Store
상세 상태   → ViewModel
화면 효과   → Composition

생성된 구현이 기존 설계와 맞는지 판단할 때 다음 지점을 살폈습니다.

  • 상태의 소유자와 정리 시점
  • 코루틴의 취소·중복 요청 처리
  • 컴포넌트가 연결되는 화면 이동과 사용자 흐름
